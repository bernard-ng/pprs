# P12 robustness and performance baseline

Measured 2026-10-17 on Apple M5 (10 logical CPUs, 16 GiB RAM), Darwin 27.0.0, aarch64-apple-darwin, Rust 1.99.0 (`b940084d7`, LLVM 23.1.1). This checkpoint builds on `58fbd10`; the raw reports pin the actual measured source files by SHA-256, including the P12 traversal change. The base commit alone does not identify the modified implementation.

## Reproduce and interpret

```sh
python3 tools/perf/measure.py --output target/performance.json --cold-target target/performance-cold
python3 tools/robustness/campaign.py --output target/fuzz-campaign --seconds 120 --bootstrap-stable
```

Use new output paths and stop other CPU/memory-heavy work. The fuzz fallback is specific to this run; prefer installed nightly as described in the [campaign guide](../../tools/robustness/README.md). The [measurement guide](../../tools/perf/README.md) describes dataset construction and measurement boundaries. No PHP/reference checkout is required. Rust dependencies and the 300-fixture input corpus are pinned.

[Raw baseline](p12.json) retains nine samples per workload, calibration iterations, per-input result/allocation metadata, both process resource reports, build commands, dependency versions and source hashes. Each timed batch includes source copying/indexing, lexing or full parsing, and drop. Timing uses the normal allocator; the separate allocation executable uses a counter around the system allocator. The cold build uses an empty target directory with warm registry/download caches. No competing project fuzz/test/build jobs ran during the final measurement.

Results are a descriptive baseline for this machine, not a throughput promise, confidence interval, cross-language comparison or CI performance threshold. The valid/invalid fixture batches are small real syntax examples, not representative application repositories. Synthetic cases expose width, depth and limits. Input generation/loading and JSON reporting are outside timed loops but inside process RSS. A fresh run will vary with allocator and system state.

The 20,000-argument call, 10,000-member class, 10,000 statements, 1 MiB comment, 50,000-line heredoc and 16 MiB whitespace/newline cases complete cleanly. The long chain stops at the depth bound; the error storm exhausts diagnostics. The node workload exhausts nodes. The token workload exhausts tokens in lex-only mode and hits the node budget first during full parsing. Only 5 of the invalid corpus's 5,329 bytes are left unscanned; retained halt data is a separate deliberate boundary from an unscanned abort suffix. Standalone lexing can diagnose halt tail bytes that the parser preserves as raw data, so the valid corpus's lex-only status is not uniformly clean.

## Allocations, result size and process memory

Allocation counts exclude reallocations (reported separately in JSON). Retained heap is allocated minus freed bytes while one result remains alive; corpus rows sum those independently measured live sizes, not concurrent residency. Inline values are 112 bytes for `ParseResult` and 88 bytes for `LexResult` on this target; retained heap is additional storage. Process peak RSS measures resident pages, not requested allocator bytes, and can therefore be smaller or larger than the retained-heap estimate.

Single-batch RSS uses the allocation-counter executable, each input once in sequence. Repeated RSS uses the normal timing executable including warm-up, calibration, metadata collection and all repetitions. Neither isolates a result from loaded inputs/runtime/allocator behavior.

| invalid | 4,736 | 0.484 | 12.84 | 12.97 |
| statements | 390,011 | 42.469 | 48.06 | 118.98 |

The newline boundary case retains about 144 MiB of requested heap for a 16 MiB input because every newline adds a line-start offset. Its single-batch process peaks around 308 MiB and repeated parsing around 1.79 GiB on this host. Wide arguments similarly have much higher repeated RSS than their retained result storage. These measurements show allocator/process high-water behavior under repetition; they do not establish a leak or an exact allocator cause. Budgets constrain parser work and structure, **not process RSS**. The existing 16 MiB / depth 128 / 1,000,000 token / 250,000 node / 100 diagnostic defaults remain the general-purpose defaults, with lower caller-configured limits appropriate to constrained memory. No new memory-quota guarantee is introduced.

## Builds and dependencies

Library-only release build: **5.148 s cold**, **0.033 s no-op warm**, peak build process RSS **339.88 MiB**, `libpprs` rlib **2,794,920 bytes**. Build peak RSS is the operating system's command report, not a sum of concurrent compiler processes. Rlib size includes Rust metadata; it is not a downstream linked-binary size.

The library still has three direct normal dependencies: `bstr`, `logos`, `thiserror`. The pinned normal dependency graph has 16 distinct dependency packages including proc-macro/code-generation dependencies (both `syn` versions count separately); it is retained in the raw JSON. The new `stats_alloc` dependency exists only in the unpublished measurement package. There is no product executable or new library runtime dependency.

## Bounded fuzzing and regression evidence

[Campaign metadata](p12-fuzz.json) pins initial corpora, source files, compiler, commands and raw-log hashes. Each byte target started from 4,036 deduplicated seeds including the empty input (libFuzzer reports 4,035 nonempty files); generated parsing started from 256 seeds. Random seeds were 12001–12003, timeout 10 seconds/input, RSS limit 2,048 MiB. Byte inputs were capped at 65,536 bytes and grammar seeds at 128 bytes. The byte campaigns' final mutation length limit was 1,015 bytes; large-input coverage comes from the deterministic stress suite, not a claim that these short campaigns explored every allowed length.

| Target | Executions | Reported seconds | Final coverage edges | Peak RSS MiB | Full log |
| --- | ---: | ---: | ---: | ---: | --- |
| lex_bytes | 796,287 | 121 | 3271 | 647 | [gzip](p12-lex_bytes.log.gz) |
| parse_bytes | 101,419 | 121 | 10140 | 701 | [gzip](p12-parse_bytes.log.gz) |
| parse_generated | 210,231 | 121 | 2117 | 690 | [gzip](p12-parse_generated.log.gz) |

All three runs returned zero with no sanitizer findings, crashes, timeouts or invariant failures. This host could not resolve the nightly download endpoint; the explicit stable bootstrap fallback retained ASan and inline coverage instrumentation. Binary linkage to `librustc-stable_rt.asan.dylib` was checked. These are bounded local observations, not exhaustive correctness or a portable stable-fuzzing guarantee.

Before the final campaign, lifecycle stress exposed a test-only JSON projection stack overflow at 110 unary operators on a 2 MiB debug worker stack. The [decision and regression](../decisions/0011-robustness-and-performance.md#minimized-stack-regression) document minimization, isolation and the scoped projection-worker fix. Production parsing, traversal, clone/equality/Debug, serialization through the test adapter and drop now pass the tested depth boundaries; the parser still caps depth at 128. All pre-existing compatibility comparisons remain unchanged.
